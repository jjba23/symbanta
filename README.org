Symbanta  is a  privacy-friendly, free and open-source software analytics platform.

It tries to inspire a return to what measurement should be: tracking *what happened so as to improve user experience and reliability*, not for profit and selling customized ads to people.

Symbanta (Greek: *Συμβάντα*, singular *Συμβάν* / *Symban*) originates from the Ancient Greek verb /συμβαίνω/ (/sumbainō/), a compound of /syn-/ ("together") and /bainō/ ("to step or walk"). It translates to: /events, occurrences, or happenings/.

Instead of profiling individuals or building invasive cross-site identities, Symbanta treats data as pure, objective, self-contained system occurrences, moments where intent and action converge. Its open and free ethos honors its Greek roots of public transparency and shared knowledge, giving developers event-driven insights while fully preserving user privacy.

* Technical Architecture

Symbanta is organised as a hexagonal (ports and adapters) application. Dependencies point inwards: the domain and the application layer never import Spring, JPA, JDBC, HTTP or the generated OpenAPI classes.

#+begin_src text
  feature/<name>/domain                        plain Kotlin entities and domain services
  feature/<name>/port/inbound                  use cases the application offers
  feature/<name>/port/outbound                 capabilities the application needs
  feature/<name>/service                       use case implementations
  feature/<name>/adapter/inbound/...           HTTP controllers, security SPI, seeders
  feature/<name>/adapter/outbound/...          Spring Data JPA repositories, CDN headers, queue workers
  shared/{domain,port,adapter}                 identifiers, reporting periods, errors, clock
  config/                                      composition root
#+end_src

Everything is grouped by feature, and inside a feature by the hexagonal role:

- ~events~: ingestion (validate and enqueue), the durable writer, the bounded queue, geolocation.
- ~statistics~: summary, time series, routes, screen sizes, user agents, events and countries; the
  read-side query port with two adapters — one answering from the hourly and daily rollup tables, one
  aggregating the event log directly — plus the background refresher that maintains them.
- ~properties~, ~eventtypes~, ~auth~, ~console~, ~telemetry~: one feature per domain concern, each with its own ports, services and adapters.
- ~shared~: the kernel every feature may depend on — =PropertyId=, =EventId=, =DateRange=, =TimePeriod=, the reporting period resolver, the exceptions and the clock port.
- Composition root: ~config/WiringConfig~ is the only place where ports are bound to implementations. Replacing PostgreSQL, or the in-process queue for a broker, is a change confined to that file.

Dependencies only ever point inwards: =domain= has no framework imports, =service= only knows its feature's ports, and adapters implement ports. A feature never reaches into another feature's adapter or service.

The server backend is implemented using modern infrastructure designed for high throughput, strict domain isolation, and non-blocking asynchronous processing:

- Telemetry Snippet: Integrating symbanta into your project is extremely lightweight and customizable ✨, even See [[file:src/main/resources/js/symbanta.js][vanilla self-contained JavaScript client]] (~10 KB, ≈2.5 KB gzipped) containing zero external dependencies.

- Asynchronous Event Queue: Fire-and-forget ingestion over a bounded Kotlin Coroutines queue (a fixed worker pool on =Dispatchers.IO=). The API always answers =202 Accepted= immediately while database writes happen off the HTTP thread pool. Workers coalesce whatever is queued into one batched write (Hibernate JDBC batching) per flush, so throughput is bound by batches rather than events. When the burst exceeds the queue capacity the excess is dropped with a rate-limited warning (and a counter) instead of exhausting the JDBC pool or the heap.

- Storage Layer: PostgreSQL accessed through Spring Data JPA (Hibernate), with native =jsonb= document support for extensible payload properties, managed strictly via Flyway schema migrations. Entities map the tables and Spring Data repositories provide the CRUD. Dashboard reads are native SQL: window functions (`LAG`) over the event log, and the rollup pipeline (~StatsRollupRefresher~, ~RollupAnalyticsQueryAdapter~) over =JdbcTemplate=, so its bucket boundaries and session stitching stay explicit.

- REST API Runtime Environment is Java 25 & Kotlin 2.4 built upon Spring Boot 4.1.

- Contract-Driven Interface: OpenAPI 3.0 specification ([[file:src/main/resources/openapi.yaml][openapi.yaml]]) driving automated model and Spring Web controller generation via Fabrikt.

* API Specification Summary

Symbanta exposes a REST API defined at [[file:src/main/resources/openapi.yaml]].

*** Public & Ingestion Routes

=POST /v1/events/register=
Ingests anonymized events. Any event name is accepted: the built-in ones (=page-view=, =heartbeat=,
=visibility-change=, =console=) and arbitrary custom/business events. The request context
(allow-listed headers, referrer, coarse country) is captured server-side.

=GET /symbanta.js=
Serves the static telemetry client JavaScript snippet.

*** Analytical Dashboard Routes

=GET /v1/properties=
Lists all domains registered for telemetry tracking.

=GET /v1/stats/summary=
Calculates privacy-safe metric aggregates (=pageViews=, =visitors=, =bounceRate=, =averageDurationMillis=) over standard periods (=LAST_24_HOURS=, =LAST_7_DAYS=, =LAST_30_DAYS=, =LAST_6_MONTHS=, =LAST_12_MONTHS=, or =CUSTOM=).

=GET /v1/stats/timeseries=
Outputs time-bucketed (hourly or daily) metrics for graph rendering. Buckets are zero-filled and
start at the local hour/day in =Europe/Amsterdam= (the reporting time zone), independent of the
database session time zone; the requested window is half-open, so =to= is exclusive. Long windows
are bounded to their most recent 500 buckets, so =ALL_TIME= covers roughly the last sixteen months;
=from= in the response is the first bucket actually returned.

=GET /v1/stats/events=
Occurrence counts and distinct visitors per event name, including custom and business events.

=GET /v1/stats/countries=
Page views and visitors grouped by the coarse country of the client.

=GET /v1/event-types= and =POST /v1/event-types=
List or declare the event names an application may emit. Registration is idempotent.

=GET /v1/logs=
Recent ~console.log~ / ~console.error~ output forwarded by instrumented applications, filterable by level.

* Custom events, console capture and request context

** Custom events

Any event name is accepted, no migration or schema declaration is required: the first event of a
new name registers the event type for that application automatically and makes it visible through
=GET /v1/event-types= and =GET /v1/stats/events=.

#+begin_src javascript
window.symbanta.track("checkout-started", {cartSize: 3, currency: "EUR"});
#+end_src

Declarative markup works without JavaScript, when =data-track-clicks= is enabled:

#+begin_src html
<button data-symbanta-event="signup-click" data-symbanta-props='{"plan":"pro"}'>Sign up</button>
#+end_src

** Console capture

With =data-capture-console= the snippet mirrors browser console output into Symbanta as =console=
events (the original console methods still run). Read them back with =GET /v1/logs=.

** Request context

Every ingested event stores an allow-listed subset of request headers (=user-agent=,
=accept-language=, =referer=, =origin=, =accept=, =sec-ch-ua*=, =dnt=, =sec-gpc=), the referrer
(falling back to the =Referer= header when the payload omits one) and the coarse country of the
caller. The country is resolved from CDN/proxy headers (=CF-IPCountry=, =X-Vercel-IP-Country=,
=CloudFront-Viewer-Country=, ~X-Country-Code~, ~X-AppEngine-Country~, ~X-Geo-Country~). The raw IP
address is used at most for that lookup and is never stored, in line with the project's privacy
principles.

* Properties

* Authentication / Authorization

The routes to view analytics for a property are protected by authentications and Spring Web.

You should use the ~/auth/login~ route for a session token.

#+begin_src yaml
application:
  user-seeder:
    users:
      - username: admin
        password: password123
        role: ROLE_ADMIN
#+end_src

* Observability

Ingestion overload is visible from outside the JVM: the queue adapter publishes Micrometer meters that
Actuator exposes in Prometheus format at =GET /actuator/prometheus=.

| Meter                                      | Type      | Meaning                                              |
|--------------------------------------------+-----------+------------------------------------------------------|
| =symbanta_ingestion_queue_backlog=          | gauge     | Events accepted but not yet written (queue backlog)  |
| =symbanta_ingestion_events_enqueued_total=  | counter   | Events accepted from HTTP                            |
| =symbanta_ingestion_events_processed_total= | counter   | Events durably written                               |
| =symbanta_ingestion_events_failed_total=    | counter   | Events lost because their batch could not be written |
| =symbanta_ingestion_events_dropped_total=   | counter   | Events rejected because the queue was full           |
| =symbanta_ingestion_batch_events=           | summary   | Events coalesced into one write (count, sum, max)     |
| =symbanta_ingestion_batch_flush_seconds=    | timer     | Time spent persisting one batch                      |

Alert on =increase(symbanta_ingestion_events_dropped_total[5m]) > 0= (traffic exceeds the write
budget) and on a backlog that does not drain (=symbanta_ingestion_queue_backlog= growing while
=processed= stalls).

=GET /actuator/health= and =GET /actuator/prometheus= are reachable without a session so probes and
scrapers work out of the box; the rest of =/actuator/**= requires =ROLE_ADMIN=. The metrics contain
only aggregate counters and timings, but if the endpoint is exposed to the internet, restrict it at
the reverse proxy (or move =/actuator/prometheus= behind =ROLE_ADMIN= in ~config/SecurityConfig~).
Exposed endpoints and the ingestion knobs live in ~application.yaml~:

#+begin_src yaml
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus,metrics

application:
  ingestion:
    queue-capacity: 10000
    worker-count: 8
    max-batch-size: 500
    # How long a worker lets its batch fill before writing it (0 = write immediately)
    linger-millis: 10
  # How long a stats read may be served from memory (0 = read the store on every call)
  stats:
    cache-ttl: 15s
    # Hourly and daily rollups: how often the hour in progress is rebuilt, and whether dashboard
    # reads use them at all (false aggregates the event log per request)
    rollup:
      enabled: true
      refresh-interval: 15s
#+end_src

* Benchmarks

Performance work is measured, not guessed. Two complementary harnesses live in the repository:

1. *JVM benchmarks* (~just bench~): dependency-free harness that warms up, runs several rounds and
   reports the best result for the pure domain services (user agent parsing, screen size bucketing,
   reporting period resolution), for the request path (validation + enqueue) and for a worker batch
   write of 500 events wired to in-memory adapters. No database or network is involved, so the
   numbers describe Symbanta's own code.
2. *HTTP load tests*, two interchangeable drivers:
   - [[https://k6.io][k6]] (~just bench-http~, ~just bench-query~): constant-arrival-rate ingestion and
     dashboard read load, with thresholds. This is the canonical harness.
   - ~bench/http_load.py~ (stdlib only, no install): ~python3 bench/http_load.py ingest
     --concurrency 8 --duration 10~ and ~python3 bench/http_load.py query --username admin
     --password ...~. Used for the numbers below on a machine without k6.

Because ingestion is fire-and-forget, the HTTP benchmarks describe acceptance latency; the durable
write throughput is visible in =events= table growth and in the JVM pipeline benchmark. Record the
numbers of the machine you deploy on: absolute values are machine dependent, regressions between two
revisions on the same machine are what matter.

** Current measurements

Local run: 12 vCPU, Java 25, PostgreSQL 17 (Podman), API and load generator on the same machine.
Treat these as a regression baseline, not as a capacity promise.

A first load pays for aggregating the window from the rollup tables; reads inside the cache TTL, and
the reads of every other user or tab, are answered from memory.

** Pre-aggregated dashboard reads

Dashboard endpoints do not aggregate the event log. Two tables hold the same facts one bucket at a
time, maintained by ~StatsRollupRefresher~:

- =stats_session_bucket=: one row per session per =hour= and per =day=, with event and page-view
  counts plus the active time measured between consecutive events inside that bucket.
- =stats_dimension_bucket=: one row per session per bucket per dimension (=route=, =country=,
  =screen=, =user_agent=, =event=).

Rows keep the session id instead of being reduced to a count, because visitors are *distinct*
sessions: a tab stays active across many buckets, so summing per-bucket counts would count it twice.
With the session key present, a bucket can still be aggregated exactly — page views sum, visitors are
counted distinct, and the active time of a session that spans buckets is stitched back together with
=LAG= at read time.

The refresher rebuilds the whole hours that have completed, rebuilds the hour in progress on every
tick (=application.stats.rollup.refresh-interval=, default =15s=), and derives the day rows from the
hour rows. A run is one transaction, so a bucket is never observed half-built, and it advances a
coverage watermark (=stats_rollup_state=) saying how far the tables are valid. Buckets are rebuilt
rather than patched, so an event that commits after its hour was rolled up is picked up by the next
rebuild of that hour.

Reads are split by ~RollupWindow~ into four contiguous slices: whole days come from day rows, the
rest of the covered window from hour rows, and the event log answers the minutes before the first
whole hour plus anything after the watermark. That is what keeps windows that do not start on the
hour exact (a =LAST_24_HOURS= window starts at, say, 10:37), and what lets a deployment with no
rollups yet answer correctly: with no coverage, everything is read from the event log.

- Rollups are switchable: =application.stats.rollup.enabled= (default =true=; =false= aggregates the
  event log per request and stops building rollups).
- Both adapters are pinned by the same contract: ~RollupAnalyticsQueryAdapter~ runs the full
  ~AnalyticsQueryPortContract~, and a differential spec compares it with the direct adapter over
  randomised sessions, tabs spanning hours and local midnight, and windows that start and end
  mid-hour.

** Caching dashboard reads

On top of the rollups, =CachingStatisticsQueryService= answers a repeated read from memory:

- It is keyed by view, application and period, and a value is reused for at most
  =application.stats.cache-ttl= after it was computed (default =15s=, =0= disables it). The window
  reported in a cached response is the one it was computed with, so the freshness loss is bounded by
  the TTL and visible in the payload.
- It collapses concurrent first reads: one request computes a key and the rest wait for that answer.
- It is observable: =symbanta_stats_cache_hits_total=, =symbanta_stats_cache_misses_total= and
  =symbanta_stats_cache_entries=.

** Testing outbound adapters

The analytics outbound ports have reusable contract suites:

- ~AnalyticsQueryPortContract~ (statistics) and ~EventStorePortContract~ (events) live next to their
  ports under ~src/test/kotlin~ and take a small fixture that creates the adapter, seeds a property
  and resets state.
- Both analytics adapters extend ~AnalyticsQueryPortContract~ (the rollup one rolls its seeded
  events up first, the JPA one reads them back through the entity layer), so aggregation, ordering
  and window semantics cannot silently diverge between them. A differential spec additionally
  compares the two on randomised traffic.
- ~support/TestPersistence~ boots a minimal JPA context (datasource, entity manager, transactions,
  repositories) against the Testcontainers database, so the specs exercise the same Spring Data
  proxies and `@Transactional` boundaries as the running application.
